# Tutorial validation — 9 November 2026

The tutorials use hypothetical business stories, original illustrations and real extension screenshots populated with fictional state. The login capture is the public RELAYERS sign-in page, with no credentials. Screenshots are explanatory material, not evidence of a customer deployment.

The opt-in `test:bridge:live` test used the pre-existing dedicated QA account against the real RELAYERS service. It approved a device through the real panel, created separate IN/OUT endpoints, exercised real webhook ingestion, queue/worker delivery and the signed browser tunnel, and verified duplicate-command suppression. No maintainer or customer WhatsApp account was used.

For the first-case validation, the test also registered a separate application tunnel in that QA account, attached an IN route only to that application, delivered the actual event through that tunnel to a loopback HTTP receiver, and submitted a reply through the public OUT endpoint without a RELAYERS login token or browser cookie in that send request. The application tunnel maps one fixed test destination to its own loopback receiver; it never proxies arbitrary URLs. Temporary endpoints and both QA daemons were removed afterward.

WhatsApp was simulated throughout. Checks retained the actual browser document handle, in-memory token, composer draft, active chat, URL and work-tab focus. There were no WhatsApp navigations or real recipient sends. The application and browser ran on the same physical test host; an application on a physically separate remote host and a public HTTPS receiving destination were not exercised in this run. The independent public OUT request supports the documented separation from the browser session but is not a geographic-distance test.

`test:tutorials` checks both libraries and all sixteen articles in real Chromium: static content, working local navigation, readable image files, login destination, receiving/sending diagrams, location controls, keyboard operation, image enlargement, equivalent-story language switching and 320/390/1440 pixel layouts. External requests are blocked and analytics consent is rejected, so the test sends no Google statistics.

Rebuild with `npm run build:tutorials`. Refresh screenshots only with `npm run capture:tutorials`; its extension captures use fixtures, and its only live page is the unauthenticated public sign-in screen. The original AI illustration is in `site/tutorials/assets/connected-business.png`. Its built-in imagegen brief requested an isometric bakery and remote desk linked by a blue/teal ribbon, navy background, warm shop lighting, tactile materials, no text, logos or readable interface. The three scenario covers are editable original SVGs produced by the tutorial builder.

Three additional guides cover RELAYERS itself for nontechnical readers. They use a separate article presentation with plain-language diagrams and questions, without WhatsApp directions, Bridge setup or claims of live business-case verification. Browser checks enforce that separation, resource loading, equivalent-story language switching and small-screen readability. Their content follows the service’s public account and Desktop guidance; it does not claim that every third-party tool can be connected without assistance.

The 0.2.0 configuration test used the actual Bridge page to choose Basic/Advanced filters, select an independently registered application daemon, create its IN route and update the same rule through the real service. It verified that an excluded incoming fixture never reached the application and that an unmatched OUT was rejected before dispatch. A matching OUT then completed the round trip. Local fixture tests separately cover remote-route payloads, failed updates, recovery, removal of only the managed IN route and preserved OUT routing. Unit tests cover filter boundaries, no backfill of excluded content, stable OUT rejection, and Disconnect during an unfinished save.
